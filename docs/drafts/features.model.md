### The record

Skeinwise stores the record as one SQLite file in ~/.skeinwise and Markdown notes in ~/.skeinwise/notes. The database includes tables for sources, threads, entries, and versions. An entry is a single message, note, or file with a type, speaker (you, assistant, or a named person), thread, source, created date, and content hash. Original data is append-only. Editing an entry adds a new version with the editor's name and date. No original data is overwritten. A conversation marked 'not mine' removes it from the Map, search, and notes but keeps it in the history. The record is a collection of these entries, organized by threads and sources. Each entry has a unique content hash to ensure data integrity. The versions table tracks all changes to an entry. The record is a structured, versioned collection of user and assistant interactions, notes, and files. It is designed to be a reliable, long-term storage of a person's digital conversations and notes.

### Importers

Skeinwise supports multiple import methods. ChatGPT exports conversations.json, which tracks the active branch of each conversation. Claude exports conversations.json as well. Gemini Takeout uses MyActivity.json, grouping prompts into threads by 30-minute gaps. Claude code history is found in ~/.claude/projects/*/*.jsonl, containing text only with tool calls removed. Codex history is in ~/.codex/sessions/**/*.jsonl. Markdown folders and Obsidian vaults are supported, using front matter, [[links]], and #tags. Dates are taken from front matter, file names, or modified times. All methods accept zip files or folders. Unknown fields are skipped, and missing fields do not cause errors. Each importer converts data into a single dated record. The system organizes tags, links, and summaries without altering the original files. Users can explore the data as a 3D map and ask questions. AI agents use the record as memory.

### Dedupe and versions

Each entry is keyed by source and the external id. Re-importing the same export adds nothing. A changed text becomes a new version, and the newest one counts. Identical text arriving from two exports of the same conversation is stored once. The system ensures that each piece of content is uniquely identified based on its origin and external identifier. If the same data is imported again, it is not added again. When text is modified, it creates a new version, with the most recent version being the one that is used. If the same content appears in two different exports but is from the same conversation, it is stored only once. This helps keep the records clean and avoids duplication. The versioning system allows users to track changes over time. The deduplication process ensures that the records remain accurate and efficient. The system is designed to handle multiple sources and versions without confusion. Users can rely on the system to manage their data correctly.

### Search

Search through all records using full-text search on titles and bodies. The search uses SQLite FTS5 with stemming to find related terms. Results are ranked by relevance, with your own words given higher priority. You can filter results by source, speaker, date range, folder, or tag. The search also finds similar entries using term vectors (TF-IDF cosine) to match based on content. Search results can be displayed as points on the Map for visual exploration. You can click on a point to view the record. The search interface is simple and direct, allowing you to quickly find what you're looking for. The ability to search by date range helps you find records from specific periods. Filters make it easier to narrow down results to what you need. The combination of text search and term vector similarity ensures you can find related records even if they don't use the same exact words. The Map view provides a spatial representation of search results, helping you understand the relationships between records. This search functionality is designed to be efficient and intuitive, making it easy to find and explore your records.

### Ask

A question in plain words becomes a view: the organiser picks the entries that answer it and lists them by date, with the person's quotes first. Patterns like 'when did I first …', 'what did I decide about …', and 'what changed in my thinking on …' are supported. With a model engine, a short answer is written on top, citing entry ids. Without AI, the view is built from search and dates only. The person can explore the answers in context, seeing how their thoughts evolved over time. The organiser uses the full text of entries to find relevant information, not just keywords. The view is ordered by date to show the timeline of thinking. The person's own words are prioritized to maintain authenticity. The model engine provides a concise summary, but the full context is always available. The view is flexible, adapting to the question asked. The person can refine the question to get more precise results. The system supports both structured and unstructured questioning. The organiser ensures that the answer is grounded in the original records. The person can use this to track their own thought processes and learning.

### The organiser and runs

The organiser performs tasks like tagging, filing, linking, and creating hubs. Hubs group entries by topic with summaries and open questions. Layers refine entries with cleaned, expanded, digest, or idea versions. Reviews note entries that may be outdated.

Each task is a run. A run includes the task, engine, model, scope, status, counts, token use, and start/end times. The run id records all changes made during the run. Undoing a run deletes all its changes.

Runs cover large scopes by showing a size estimate first and waiting for approval. The organiser tracks every run's details. Each run is a separate process that records its own id. The system ensures runs are manageable and transparent.

### Engines

Skeinwise uses keyword extraction based on TF-IDF to identify important terms in the record. Terms are clustered using k-means to form hubs and folders. Links are evaluated for similarity to determine connections. Extractive summaries are created for layers. The system can use any OpenAI-compatible chat endpoint, including llama.cpp's llama-server, Ollama, LM Studio, or a hosted API with a key. The model is asked to generate JSON, and its output is checked before being saved. The same tasks apply whether using a local or remote engine. The model's response is validated to ensure accuracy. This process works seamlessly with either type of engine. The system does not rely on any specific AI model beyond what is provided. All outputs are checked and verified before they are stored. The engine selection does not affect the core functionality of the system. The model's responses are used to build the structure of the record. The system is designed to work with any compatible model. The validation step ensures that the data is correct before it is saved. The process is consistent across all engine types.

### Tagging schemas

A schema is a named list of tags with descriptions. Built in: Topics, Projects, Moods. Custom schemas can be added. Before a run: a sample test on 20 entries, then the full size and cost estimate. After: coverage (share of entries tagged) and a comparison with an earlier run of the same schema (tags added, removed, unchanged). Schemas help organize and categorize entries consistently. Users can create their own schemas to fit specific needs. The built-in schemas are designed for common use cases. When a schema is run, it applies the tags to the entries based on the defined list. The sample test ensures the schema works as intended before full deployment. The cost estimate helps users understand the resource requirements. After the run, coverage shows how many entries were tagged. A comparison with previous runs highlights changes in tagging over time. This helps track improvements and adjustments. Users can refine schemas based on the results. Schemas are a key part of organizing and managing the record. They make it easier to find and understand the data.

Originals remain unchanged. Corrections are transparent. Users can review and reverse any change. The system supports reversible edits. All correction actions are designed for undo. ### Notes

Notes are stored as markdown files in the directory ~/.skeinwise/notes. They can be edited using the app or any text editor. Links within notes are converted into note links, allowing easy navigation between notes. A daily note is created for each day, providing a consistent record of thoughts and reflections. Notes written by an AI agent are marked with the agent's name, helping to identify their contributions. Each time a note is saved, a new version is created, ensuring a history of changes. This versioning allows users to track the evolution of their notes over time. The structure of notes supports both personal reflection and structured information. Users can access and modify notes from any device with access to their local storage. The system does not alter the original notes, only creates versions. This approach ensures that the original content remains unchanged while providing a record of all modifications. Notes serve as a central repository for personal and organizational information, making them a key component of the second brain system.

### Review

The organiser compares each note with newer entries on the same topic. If the newer entries disagree or add a lot, the note goes into the Review queue with the reasons. The person decides: update (with a diff), still holds, or skip. The Review queue is a list of notes that need attention. Each entry in the queue includes the note, the newer entries, and the reasons for review. The person can view the notes in a list or in a timeline. When a note is updated, the changes are saved as a diff. The organiser does not modify the original notes. The person can also choose to keep the note as is. If a note is skipped, it remains in the queue until the person decides to review it again. The Review process helps ensure that the record is up to date and accurate. It allows the person to maintain control over their data. The system is designed to be simple and efficient. The Review queue is a key part of the organiser's workflow. It helps the person stay organized and informed.

### Privacy

No AI or local engine processes data outside the user's computer. Before any text is sent to a hosted model, redaction replaces personal information like names, emails, phone numbers, street addresses, and health terms with placeholders. A preview shows what will be sent. A monthly token budget pauses runs when the limit is reached until the month resets. The record folder is created with owner-only permissions, ensuring only the user can access it. The server listens on 127.0.0.1, which is the local loopback address, meaning it only accepts connections from the same device. A per-install token is required for the server to function, adding an extra layer of security. All data remains on the user's device unless explicitly sent to a hosted model after redaction. The system is designed to minimize data exposure while allowing users to control how their information is handled.

Configurations for Claude Code, Claude desktop, Codex, Cursor, and other models are provided as code snippets for easy copying. Each agent's activity is versioned under their name. When a lock is applied, all tools are disabled. The system is designed to let agents interact with their memory in a structured way. Agents can use the tools to query, retrieve, and manage their data. The versioning ensures that each agent's contributions are tracked. The lock feature provides a way to prevent accidental changes. The configurations allow users to integrate the system with different AI models. The tools are focused on enabling agents to work with their memory efficiently. The system is built to support the needs of users who want to manage their AI interactions in a local and open manner.

### Ledger and proof of date

Each time a user imports, edits, or runs the app, a line is added to ledger.jsonl. This line includes a hash that is chained to the previous line, creating a sequence that can be verified. If someone tries to tamper with the data later, the chain of hashes makes it detectable. Users can choose to stamp the latest ledger hash with OpenTimestamps. This stamps the record with a date and time, proving it existed at that moment. The proof is fetched a few hours after stamping and stored locally. This ensures the record's date is verifiable and cannot be altered without detection. The timestamp proof is separate from the main record and is stored in the same location. Users can check the proof to confirm the record's date and integrity. The chaining in ledger.jsonl and the timestamp proof together provide a way to verify the record's history and authenticity. This system ensures that the user's data remains secure and tamper-proof over time.

### Encrypted sync

Sync writes an encrypted bundle of the record using AES-256-GCM. The encryption key is derived from a passphrase with scrypt. The bundle is saved to any folder the person chooses, like a cloud drive folder. Another computer can join the system using the passphrase. A 24-word recovery phrase, displayed once, can also restore the record. The recovery phrase is not used for encryption but for recovery. No data is sent to a Skeinwise server. There is no central server. The encryption ensures that only the person can access the record. The bundle is self-contained. The person controls where the data is stored. The system does not rely on external servers for storage or access. The encryption and recovery mechanisms ensure data privacy and reliability. The process is local-first and open-source. The person remains in control of their data. The system is designed for privacy and security.

### Command line

`skeinwise init` creates a new workspace. `import <path>` adds a directory of files to the workspace. `search <words>` finds records containing the words. `ask <question>` queries the system for information. `run <task>` executes a predefined task. `runs` lists all tasks that have been run. `undo <run>` reverts a task to its previous state. `note <text>` adds a new note to the workspace. `serve` starts the application. `mcp` runs the agent server. `demo` builds a sample record for testing. `export` generates a zip file of a record. Each command interacts directly with the system to manage data, execute tasks, and organize information. The command line provides a straightforward way to control Skeinwise without a graphical interface. Users can perform actions like importing files, searching for content, running tasks, and exporting records. The commands are designed to be simple and intuitive, allowing users to work efficiently with their data. The command line is a core part of Skeinwise's functionality, offering a flexible and powerful way to interact with the system.
